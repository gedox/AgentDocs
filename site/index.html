The problem

Docs are written for humans. Agents need specs.

You paste a documentation link into your coding agent. It skims, invents the rest, and you spend the afternoon correcting architecture it hallucinated on turn one.

01

Context you can't fit

Real documentation runs to hundreds of pages. You can't paste it, and half of it is navigation chrome anyway.

02

Prose, not requirements

Docs explain how to use software. An agent building it needs inputs, outputs, states, edge cases — the things tutorials leave implicit.

03

Sending code context to a cloud

Internal or client documentation often can't leave the building. Most tooling assumes it can.

How it works

Three steps, one machine.

STEP 01

Point it at a documentation site

AgentDocs discovers every page — via sitemap.xml and by crawling the nav — then shows you the full tree and waits. Nothing is written until the list matches what you see on the site. It handles JavaScript-rendered docs that ordinary scrapers return empty.

STEP 02

Get clean Markdown, structured like the site

One .md per page, navigation and footer chrome stripped, folders mirroring the site's own categories, plus an index. Readable by you, parseable by anything.

STEP 03

Turn it into a blueprint with your local model

Pick any model you have in Ollama. AgentDocs works through the docs category by category and writes a functional specification — numbered requirements, behaviours, edge cases, a suggested architecture and a glossary. Hand that to your agent instead of a link.

documentation · vault.md
A vault is a folder on your local file
system where notes are stored. You can
keep all your notes in one vault, or
create several vaults for different
projects.

The first time you open the app, you'll
be asked to add a new vault. You have
two options, either create a new empty
vault, or use an existing folder.
blueprint · 01-getting-started.md
FR-1: Vault creation
FR-1.1 System MUST support N vaults, N ≥ 1.
FR-1.2 A vault maps 1:1 to a filesystem
       directory. No nested vaults.
FR-1.3 Two entry paths MUST exist:
       create-empty | adopt-existing-folder.

FR-2: First-run state
FR-2.1 On launch with 0 vaults → prompt.
FR-2.2 Vault name: required, non-empty.
FR-2.3 Target path MUST be writable;
       otherwise surface a recoverable error.

Edge cases
· Target directory is already a vault
· Path on removable / disconnected drive
